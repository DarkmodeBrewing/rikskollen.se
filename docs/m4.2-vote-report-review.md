# M4.2 — vote and report design slice

Branch: `m4/design-votes-reports`, based on main `1439493` after the member-design PR #15 was merged and deployed. Scope agreed: carry through the member-page spacing, improve loading/error states, add a vote-choice result chart, and lead with readable source text across listings, detail pages and member histories. No new search/sort feature or ingestion scope is included.

## Behaviour and evidence

- Vote topics prefer an exactly matched proposal-point heading, then an imported report title. Missing text is explicitly labelled. Report titles and proposal headings lead their own views; document references and point numbers remain visible below/as quieter metadata. No generated paraphrases or political conclusions.
- Read-only API enrichment uses completed report/catalog snapshots, same-session/document matching and exact point/vote matching, with source URLs/import times. Catalog-only context supplies a title, not a decision trail. Paging, source rows, counts and summary denominators remain unchanged. See [methodology](data-methodology.md#m42-readable-vote-context-and-event-chart).
- Single-vote bars show exact source-choice counts, total and session. The shared chart distinguishes its single-event scope from a member-history scope; no general attendance assertion or winning-proposal inference.
- Vote/report routes use explicit loading/ready/missing/error request states. A failed import-status request differs from no completed import. Request errors stay inside switchMap so subsequent navigation can recover. Existing empty-state and source-link behavior remains.
- Roomier vote/report rows and member-choice rows, stacked mobile metadata, readable proposal measure/line spacing and explicit keyboard focus.
